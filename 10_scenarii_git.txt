10 SCENARII GIT — DE LA SIMPLU LA COMPLEX
Laborator pentru Cristian: main + contul colab

CUM FOLOSESTI ACEST FISIER
Rezolva pe rand. Cerintele sunt primele; indicii si solutiile sunt la final.
Nu trebuie sa termini intr-o seara. Explica cu voce tare ce face fiecare comanda.
Editeaza fisierele in VS Code: astfel eviti diferentele dintre PowerShell,
Git Bash, Linux si macOS. Comenzile Git de mai jos functioneaza pe toate.
In comenzile cu <HASH> sau <URL>, inlocuieste marcajul, inclusiv parantezele.

PREGATIRE UNICA
Creeaza un repository GitHub privat: git-practice-e2e, cu README initial.
Invita cristian-dinu-colab si accepta invitatia pe contul colab.
Contul principal: cristian-dinu-69. Vom numi copia lui A.
Contul colaborator: cristian-dinu-colab. Vom numi copia lui B.
Cloneaza repository-ul pe ambele calculatoare:
  git clone <URL_COPIAT_DIN_GITHUB>
  cd git-practice-e2e
  git status
  git remote -v
Verifica identitatea Git cu git config user.name si git config user.email.
Identitatea commit-ului si contul folosit pentru autentificare sunt distincte.
Alternativa fara al doilea calculator: doua clone in directoare diferite.
Poti simula modificarile A/B, dar review-ul cu doua conturi cere autentificarea
corespunzatoare. Nu schimba conturile de companie pentru aceste exercitii.

REGULI DE LABORATOR
Lucreaza exclusiv in acest repo de exercitii, fara date sau secrete reale.
Inainte de schimbare de branch: git status. Nu ignora modificarile locale.
La inceputul fiecarui scenariu, pe copia care va lucra:
  git switch main
  git fetch origin
  git merge --ff-only origin/main
Daca ultima comanda refuza, nu continua mecanic: verifica istoricul.
Verifica branch-ul cu git branch --show-current.
Pentru integrarea PR-urilor foloseste Create a merge commit, daca este disponibil.
Nu sterge branch-urile pana cand exercitiul care le foloseste este terminat.
Nu folosi force push pe main. State-urile Terraform nu au ce cauta aici.

Sarcini:

2. Verifica diferenta staged, creeaza commit-ul si publica branch-ul.
3. Deschide PR spre main si integreaza-l din GitHub.
4. Actualizeaza main local. Sterge manual scratch.txt dupa exercitiu.
Succes: intro.txt exista pe GitHub; scratch.txt nu exista acolo.

SCENARIUL 6 — CONFLICT PE ACEEASI LINIE (mediu-avansat)
======================================================================
Pregatire pe A: pe un branch separat, adauga settings.txt cu 'steps=100';
commit, push si integrare prin PR. Actualizeaza main pe A si B.
IMPORTANT: ambele branch-uri de mai jos pornesc din aceasta aceeasi versiune.
A: exercise/06-a schimba linia in 'steps=1000', commit si push.
B: exercise/06-b schimba linia in 'steps=2000', commit si push.
Integreaza intai PR-ul B. Branch-ul A ramane cu schimbarea lui.
Sarcini pe A:
1. Fetch; pe exercise/06-a, integreaza origin/main prin merge.
2. Inspecteaza conflictul si markerii lui. Decizia de laborator este 2000.
3. Rezolva fisierul, finalizeaza merge-ul si publica branch-ul.
4. Deschide/actualizeaza PR-ul A si verifica lipsa conflictelor.
Succes: nu exista markeri, working tree este curat si main are steps=2000.
Nota: pastrand numai varianta B, PR-ul A poate sa nu aiba diferenta de continut
fata de main; verifica istoricul si inchide PR-ul daca integrarea este inutila.
Intrebare: cum abandonezi merge-ul INAINTE sa il finalizezi?

======================================================================
INDICII — CITESTE DOAR DACA TE BLOCHEZI
======================================================================
1. git add poate primi un singur fisier; -u la push stabileste upstream.
2. git rm --cached; git check-ignore -v; istoricul nu este curatat de ignore.
3. git log main..origin/main --oneline; git show origin/main:team.txt.
4. git stash push -u -m 'WIP'; apply pastreaza stash-ul pana il verifici.
5. Push pe acelasi branch actualizeaza automat PR-ul.
6. git status iti arata fisierele in conflict; git merge --abort anuleaza merge-ul.
7. git add accepta fisierul pastrat; git rm accepta stergerea.
8. git revert creeaza un commit de compensare; evita hash-ul merge-ului aici.
9. git rebase origin/main, executat de pe branch-ul tau privat.
10. git reflog; git show <HASH>; git branch rescue/10-lost <HASH>.

SOLUTII ORIENTATIVE — DUPA INCERCAREA TA
======================================================================
Comenzile presupun ca esti in branch-ul indicat si ca ai editat fisierele.
Daca apare conflict sau eroare, opreste secventa si inspecteaza git status.
In GitHub, completeaza PR-ul cu problema, schimbarea si verificarea efectuata.

1. git switch -c exercise/01-first-commit
   [creeaza cele doua fisiere]
   git status
   git add intro.txt
   git diff --cached
   git commit -m "Add introduction"
   git push -u origin exercise/01-first-commit
   [PR si merge; actualizeaza main; sterge scratch.txt manual]

2. git switch -c exercise/02-ignore
   [creeaza demo.log]
   git add demo.log
   git commit -m "Track demonstration log"
   [creeaza .gitignore si modifica demo.log]
   git status
   git rm --cached demo.log
   [creeaza temp.log]
   git check-ignore -v temp.log
   git add .gitignore
   git diff --cached
   git commit -m "Ignore logs and stop tracking demo log"
   git push -u origin exercise/02-ignore
   [PR si merge]
   Fisierul demo.log ramane in istoricul commit-ului initial.

3. B: branch, team.txt, commit, push si PR ca in scenariul 1.
   A, pe main:
   git fetch origin
   git status
   git log main..origin/main --oneline
   git show origin/main:team.txt
   git merge --ff-only origin/main
   git switch -c exercise/03-followup
   [adauga a doua linie]
   git add team.txt
   git commit -m "Extend team note"
   git push -u origin exercise/03-followup
   [PR si merge]

4. Pe exercise/04-wip, dupa editarile necomise:
   git stash push -u -m "Exercise 04 WIP"
   git status
   git switch main
   git switch -c exercise/04-hotfix
   [editeaza README, commit, push, PR si merge]
   git switch exercise/04-wip
   git stash list
   git stash apply 'stash@{0}'
   git diff
   git status
   [verifica si fisierul nou in editor]
   git stash drop 'stash@{0}'
   git add intro.txt notes-wip.txt
   git commit -m "Complete WIP notes"
   git push -u origin exercise/04-wip
   [PR si merge]
   -u include fisierele untracked, dar nu si fisierele ignorate.

5. A, dupa review:
   [inlocuieste + cu * in main.py]
   git diff
   git add main.py
   git commit -m "Fix total calculation"
   git push
   [B verifica si aproba PR-ul existent; merge]

6. A, pe exercise/06-a:
   git fetch origin
   git merge origin/main
   [deschide settings.txt; pastreaza steps=2000; elimina toti markerii]
   git add settings.txt
   git diff --cached
   git commit -m "Resolve steps conflict using agreed value"
   git push
   [verifica PR-ul; merge sau inchidere conform diferentei finale]
   Inainte de rezolvare, alternativa de abandon: git merge --abort.

7. A, pe exercise/07-edit:
   git fetch origin
   git merge origin/main
   [verifica legacy.py: versiunea corectata este pastrata in working tree]
   git add legacy.py
   git commit -m "Resolve modify-delete conflict by keeping corrected script"
   git push
   [PR si merge]
   Daca acceptai stergerea: git rm legacy.py, apoi git commit.

8. Pe main actualizat:
   git log --oneline -- settings.txt
   git show <HASH_COMMIT_SIMPLU>
   git switch -c exercise/08-revert
   git revert <HASH_COMMIT_SIMPLU>
   [salveaza/inchide editorul mesajului daca apare]
   git show --stat HEAD
   git push -u origin exercise/08-revert
   [PR si merge]
   Revert pastreaza istoricul partajat; reset + force push il rescrie.

9. A, pe exercise/09-rebase, dupa integrarea PR-ului B:
   git log -1 --oneline
   git fetch origin
   git rebase origin/main
   git log --oneline --graph -8
   git push -u origin exercise/09-rebase
   [PR si merge]
   La conflict: editeaza, git add <fisier>, git rebase --continue.
   Pentru abandon in timpul rebase-ului: git rebase --abort.
   Pe un branch deja publicat, rescrierea poate cere --force-with-lease.
   Acesta verifica referinta remote asteptata; nu inlocuieste coordonarea echipei.

10. git switch -c exercise/10-lost
    [creeaza recovered.txt]
    git add recovered.txt
    git commit -m "Add recovery exercise file"
    git switch main
    git branch -D exercise/10-lost
    git reflog
    git show <HASH_PIERDUT>
    git branch rescue/10-lost <HASH_PIERDUT>
    git switch rescue/10-lost
    [verifica recovered.txt]
    git switch main
    git switch -c exercise/10-recover
    git cherry-pick <HASH_PIERDUT>
    git show --stat HEAD
    git push -u origin exercise/10-recover
    [PR si merge]
    Reflog este local si are retentie limitata. Nu garanteaza recuperarea
    modificarilor care nu au fost niciodata comise sau stash-uite.
